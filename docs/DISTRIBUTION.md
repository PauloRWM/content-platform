# Distribution automation

**Goal:** every published piece reaches more people with no extra manual work.
When a piece publishes, this system automatically prepares a **newsletter** and a
**social cross-post** for it. By default both are prepared as **drafts for a human
to approve** — nothing is blasted out autonomously until you opt in.

> **The 30-second version.** Publish a piece → the site rebuilds → a distribution
> step runs → you get a ready-to-send newsletter draft and ready-to-post social
> copy. Review, click send. That's it.

---

## How it fits together

```
 content piece (T2)                 this system (T4)
 ─────────────────                  ────────────────
 posts/*.md  ──build──▶  /feed.json  ──▶  scripts/distribute.mjs  ──▶  Channels
 (draft→publish)         (JSON Feed)      (finds NEW pieces)            ├─ newsletter  → Buttondown draft
                                                                        └─ social      → draft file / webhook
```

- **`/feed.json`** — a [JSON Feed](https://jsonfeed.org) of published pieces,
  generated by `src/pages/feed.json.js`. This is the **contract**: anything that
  shows up here gets distributed. The content pipeline (T2) just needs to make
  published pieces appear in the `posts` collection; distribution needs to know
  nothing else about how content is stored.
- **`scripts/distribute.mjs`** — reads the feed, figures out which pieces are
  **new** (not in `.distribution/state.json`), and runs each **channel** for them.
- **Channels** — small, self-contained senders. Two ship today: `newsletter` and
  `social`. Adding more is a few lines (see below).

**The trigger:** the distribution step runs automatically as part of publishing
(`npm run deploy`, and the GitHub Actions deploy once billing is restored). So
"publishing a piece" and "distributing a piece" are one action.

## Setup (once)

Everything is optional. With nothing configured, distribution still runs and
writes local draft files under `.distribution/drafts/` — so you can see exactly
what it produces before wiring up real accounts.

Copy `.env.example` to `.env` and fill in what you want to turn on:

### Newsletter (Buttondown — recommended)

We use [Buttondown](https://buttondown.email): simple, cheap, Markdown-native,
has a free tier, and an API that lets us create **draft** emails for approval.

1. Create a Buttondown account.
2. **Subscriber capture:** put your Buttondown username in
   `PUBLIC_NEWSLETTER_USERNAME`. The subscribe form (`/subscribe`, or the
   `<SubscribeForm />` component on any page) then posts new subscribers straight
   to Buttondown — no server needed.
3. **Auto-draft on publish:** copy your API token from
   *Settings → Programming* into `BUTTONDOWN_API_KEY`. Now each new piece creates
   a **draft email** in Buttondown. Open it, review, hit send.

*(For local runs, `.env` is read automatically only if you export the vars or use
a tool like `dotenv`. In CI, add them as repository **Secrets**.)*

### Social cross-post

By default, `distribute.mjs` writes a **social draft file** per piece with
ready-to-paste copy for X/Twitter (length-checked to 280 chars) and LinkedIn.
A human posts it. That satisfies "draft for approval" with zero setup.

To route drafts automatically into a queue or scheduler, set `SOCIAL_WEBHOOK_URL`
to a webhook from **Buffer, Zapier, Make, n8n, Slack, or Discord**. Each new
piece POSTs:

```json
{ "text": "<x copy>", "platforms": { "x": "…", "linkedin": "…" }, "piece": { … } }
```

Point that webhook at a "draft/needs-approval" queue (not straight-to-publish)
to keep a human in the loop for v1.

## Everyday use

Publishing already triggers distribution. To run it by hand:

```bash
npm run build          # produce dist/feed.json from published pieces
npm run distribute     # distribute any NEW pieces
npm run distribute:dry # preview only — no files, no network, no state changes
```

Useful flags (`node scripts/distribute.mjs --help` for all):

| Flag                   | Effect                                                        |
| ---------------------- | ------------------------------------------------------------- |
| `--dry-run`            | Preview what would happen; change nothing.                    |
| `--all`                | Treat every piece in the feed as new (ignore state).          |
| `--force`              | Re-distribute even already-sent pieces.                       |
| `--feed <path\|url>`   | Use a specific JSON Feed (default `dist/feed.json`).          |
| `--piece-file <path>`  | Distribute one piece from a JSON file (testing / one-offs).   |

**Where do drafts appear?**
- Newsletter → as a **draft email in Buttondown** (or `.distribution/drafts/*.newsletter.md` if no API key).
- Social → `.distribution/drafts/*.social.md` (and/or your webhook queue).

**No double-sends:** `.distribution/state.json` records what's been distributed.
It's git-ignored and local; on the manual deploy path this lives on the machine
that deploys. *(CI note: to avoid re-sending on a fresh runner, persist this file
— cache it or commit it — once the automatic Actions path is live. Tracked as a
follow-up; harmless today because deploys are run manually.)*

## Add a channel later

Open `scripts/distribute.mjs` and append to the `CHANNELS` array:

```js
{
  name: 'mastodon',
  async run(piece, { dryRun }) {
    // build your copy from `piece` (id, url, title, summary, tags, date_published)
    if (dryRun) return { status: 'drafted', detail: 'would post to Mastodon' };
    // ...call the API / write a draft...
    return { status: 'sent', detail: 'posted' };            // or 'drafted' / 'skipped' / 'error'
  },
},
```

Guidelines:
- **Draft-first for v1.** Return `drafted` and leave a file/queue entry unless the
  team has explicitly approved autonomous posting for that channel.
- **Fail soft on missing credentials.** No key → write a local draft and return
  `drafted`, don't error. Only return `error` for real send failures.
- Helpers available: `composeSocial(piece)`, `composeNewsletter(piece)`,
  `writeDraft(name, contents, dryRun)`, `slugify`, `hashtags`, `truncate`.

## The piece contract

Channels receive a normalized piece:

```ts
{
  id: string;              // stable unique id (the permalink)
  url: string;             // absolute URL
  title: string;
  summary: string;         // short excerpt
  date_published: string;  // ISO 8601 (may be empty)
  tags: string[];
}
```

`feed.json.js` builds these from the `posts` collection and is deliberately
lenient about field names (`title`/`headline`, `description`/`summary`/`excerpt`,
`pubDate`/`date`/`publishedAt`, `draft`/`status`), so it keeps working whatever
exact schema the content pipeline settles on.
